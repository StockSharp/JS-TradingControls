# AGENTS.md — StockSharp Trading Controls

Guidance for AI coding agents (and humans) working in this repository,
`@stocksharp/trading-controls`.

## What this is
The browser trading panels StockSharp's web applications are assembled from:
`ActiveOrdersWidget`, `PositionsWidget`, `TradeHistoryWidget` and
`WatchlistWidget`, plus the port they are written against (`trading-host.ts`),
the row shapes they read (`trading-data.ts`), the value formatters
(`formatters.ts`) and the element helpers they build their DOM with (`dom.ts`).
Source in `src/`, tests in `tests/`, looks in `styles/`. Bundled with
esbuild/tsc via `build.mjs`. `dist/` and `tests/_dist/` are build outputs and are
gitignored — never commit them.

Tables are rendered by `@stocksharp/grids`, a real dependency. Do not
reimplement column, sort or export logic here; if the grid is missing something,
change the grid.

## Everyday commands
- `npm run build` — build the ESM tree, the declarations and the browser bundle.
- `npm test` — typecheck + public-API check + style contract + translation-key
  list + unit tests (`node:test`). Run before every commit.
- `npm run i18n:update` — regenerate `translation-keys.json` after adding or
  removing a `t()` call. `npm test` fails until you do.
- `npm run release:check -- vX.Y.Z` — the publish gate: tag matches version, and
  nothing is depended on by path.

## A control imports nothing host-shaped
Everything a control needs arrives as one `TradingHost`. There is no translator
here, no settings singleton, no registry, no `window` access, and no `fetch`.
When a control needs something new, the answer is a new member on the port — not
an import, and not a global.

**Every port member is required.** Do not add an optional one and do not give
one a default. A half-supplied host is how a control half-works: it renders, it
looks alive, and the one capability nobody wired is discovered by a user
clicking something that does nothing. `assertHost` walks every member and every
nested member — the calls, not just the objects holding them, because
`api: {}` is the shape a half-wired host actually has — and throws naming the
path. Extend it when you extend the port, and extend `HOST_MEMBERS` /
`HOST_NESTED_MEMBERS` in `tests/fake-host.ts` with it; the port test walks both
lists and asserts each absence is reported by name.

Seven members have no call site among the four controls here (`spawn`,
`persistState`, `saveLayout`, `log`, `trading.pickInstrument`,
`marketData.resubscribe`, `marketData.getOrders`). They are not dead: the
terminal's three remaining controls — order book, order entry, trade feed — are
written against this same port today and call all seven. Do not "tidy" them
away; the reasoning is in the header of `trading-host.ts`.

Same rule for a control's own deps: a new callback is required and stated at
every call site, never `= null` with a guard.

## Text and diagnostics both go through the port
Every user-visible string comes from `host.t(key)` — the package decides no
wording. Keys are literals, never built by concatenation: `translation-keys.json`
is generated by scanning for them, and a computed key would be invisible to that
scan and would reach a user as itself.

Failures a user cannot see go to `host.log(...)`, never `console.warn`. The port
exists for exactly that, and routing through it is what makes a failure path
assertable from a test.

## The DOM belongs to the control
A control builds its own markup in a static `_buildRoot(host)` and is created
through a static `create(hostEl, state, deps)`. Nothing may clone a `<template>`
out of the page, and nothing may address an element by document-wide id or query
at document scope — every query is scoped to `this.rootEl`, which is what lets a
control be instantiated twice on one page.

`create()` calls `assertHost` **before** building, because the markup is
localized through the host: a missing host has to fail there rather than render a
panel captioned with raw English keys.

## Looks are class names, and the stylesheet ships with them
A control emits class names and never an inline style, a colour literal or a
measurement. `styles/trading-controls.css` gives those names meaning and reads
`--t-*` custom properties without declaring any; `styles/theme.css` carries a
default palette for a page that has none.

`tools/check-style-contract.mjs` runs in `npm test` and fails when a control
emits a class the stylesheet never styles, when the stylesheet misses one of the
port's `PRESENTATION_CLASSES`, when a rule reads a property the theme does not
declare, when the theme declares one nothing reads, or when a rule reads a
property **with a fallback**. Class lists are written as plain string literals
precisely so this stays checkable — do not build one by concatenation.

Two things follow from that last check. A `var(--t-x, #abc)` is banned: the
fallback keeps a rule working on a host that never declared the token, so the
host never learns it owes one and the control paints a shade from nobody's
palette. And `side-buy` / `side-sell` / `pnl-positive` / `pnl-negative` are the
only class names here that no control emits — they come back out of the host's
`TradingPresentation`, so they are declared as `PRESENTATION_CLASSES` on the port
and checked against the stylesheet from there.

## The public API is snapshot-tested
`npm test` runs `api:check`, which compares the exported types against
`tests/api/public-api.d.ts`. If you intentionally change the public API,
regenerate the snapshot with `npm run api:update` and commit it in the same
change — otherwise CI fails.

**Comment private members with `//`, not `/** */` or `///`.** The declaration
emitter drops a private member's body but keeps its doc comment, which then
attaches to whatever member comes next — or dangles at the end of the class.
Either way the snapshot changes and `api:check` fails on a change that never
touched the public API. When `api:check` reddens and the diff is a stray comment
block, this is why: convert that comment to `//` rather than regenerating the
snapshot, which would bake the leak in.

## The DOM in the tests is a fake, deliberately
`tests/fake-dom.ts` implements the slice of DOM the controls touch, and its size
is the statement of how narrow that slice is. Three of its behaviours are
load-bearing rather than approximated: `appendChild` **moves** a node and
**unwraps** a `DocumentFragment` (cells are built as fragments);
`dispatchEvent` **bubbles** until something stops it (the watchlist's favourite
star relies on `stopPropagation` to keep its click off the row); and `dataset` is
a view over `data-*` attributes (the grid writes through one, the controls read
selectors through the other). When a control starts using a DOM member the fake
lacks, add it there rather than working around it in a test.

`installFakeDom()` is a call, not an import side effect, so a test file states
that it needs a DOM. It is safe to call it after the imports because no module
here touches `document` while being evaluated — only while a control is created.

## Row shapes are wire shapes
Everything in `trading-data.ts` is optional and every numeric is `number | null`.
That is not laziness: an absent price reaches us as an omitted key from one
endpoint and as an explicit null from another. Do not tighten a field to make a
call site quieter — add the `?? 0` the call site already needed.

## Commits
Use Conventional Commits: `feat:`, `fix:`, `ci:`, `chore:`, `docs:`,
`refactor:`, `test:`, `perf:`. Use `feat!:` or a `BREAKING CHANGE:` footer for
breaking changes. Code comments and commit messages are in English.

## Releasing — read this before touching versions or CI
Publishing is automated and driven by the **version in `package.json`**.

- `.github/workflows/release.yml` runs on every push to `main`, but publishes to
  npm **only when the version in `package.json` is not yet on the registry**. A
  normal push whose version is already published is a no-op.
- **To cut a release**, bump the version and push:
  ```bash
  npm run release:patch   # or release:minor / release:major
  git push
  ```
  `npm run release:*` bumps `package.json` and commits `chore: release vX.Y.Z`
  (it needs a clean working tree, and also creates a *local* git tag `vX.Y.Z` —
  leave it alone: a plain `git push` does not push it, and CI creates the remote
  tag itself). The push to `main` triggers the workflow, which builds, runs the
  full test suite, `npm publish`es, then creates the `vX.Y.Z` tag and GitHub
  Release.
- Version policy: pre-1.0 — `feat` → minor, `fix` → patch. Reserve major for a
  deliberate 1.0.
- **Do not** run `npm publish` locally, and **do not** hand-push tags — CI owns
  publishing and tagging. The tag is an *output* of a release, not its trigger.
- Manual retry (e.g. a flaky test failed a publish): GitHub → Actions →
  **Publish package** → **Run workflow** (optional `ref` input).

## npm authentication — do not break this
Publishing uses **npm trusted publishing (OIDC)** — there is **no `NPM_TOKEN`**.
`release.yml` grants `id-token: write`; npm exchanges the GitHub OIDC token for a
short-lived publish token and signs a provenance attestation
(`publishConfig.provenance` in `package.json`).

Violating any of the following causes `npm error code E404 ... you do not have
permission` on publish:

- **Do not rename `.github/workflows/release.yml`**, and do not move the
  `npm publish` step into a different workflow file. The npm Trusted Publisher is
  bound to the workflow filename `release.yml`; a different filename fails OIDC
  claim matching. If a rename is unavoidable, first update the Trusted Publisher
  at npmjs.com → `@stocksharp/trading-controls` → Settings → Trusted Publisher to
  the new filename.
- **Do not add `NODE_AUTH_TOKEN` / `NPM_TOKEN`** to the publish step or to
  `setup-node`'s auth. A stale or placeholder token shadows the OIDC exchange.
- Keep npm ≥ 11.5.1 and Node ≥ 22.14 in the workflow (currently npm 11.6.2 /
  Node 24) — required for trusted publishing.

## `@stocksharp/grids` is a `file:` link until it is published
`package.json` depends on `file:../Grids`, so this repository expects the `Grids`
checkout as a sibling — and so do both workflows, which check it out beside this
one. Without it `npm ci` still exits 0, leaving a dangling symlink, and the whole
suite then fails on a module that "installed fine".

**`file:` must never reach the registry.** It resolves on a machine that has the
sibling and means nothing on npm: publish succeeds, and the failure is an
adopter's `npm install` resolving a path that does not exist on their disk. No
test here can catch it, because on this machine the path is real — so
`tools/check-release-tag.mjs` refuses the release while any dependency is a
local path, and `release.yml` runs it before `npm publish`. When the grid reaches
the registry, that line becomes a version range and the gate goes quiet.

**Source imports the grid's `./source/*`; `dist/` imports its built entries.**
`./source/*` is raw TypeScript and unconditional, which is what lets the terminal
bundle these controls from `.ts` and lets its CommonJS test bundle resolve a
package whose compiled entry points declare only an `import` condition. It is
also unpublishable: tsc copies a specifier through untouched, so the emitted
`dist/esm/*.js` would import a `.ts` file and an adopter's `import` of this
package would die inside `node_modules`. `build.mjs` rewrites the specifier in
the emitted `.js`/`.d.ts` only — source keeps `./source`, dist depends on
`@stocksharp/grids/<name>`, and neither package has to be built for the other to
work. CI proves it by actually importing `dist/esm/index.js` in node; keep that
step.

## Pushing to main is publishing
Because a version-bumping push to `main` releases a public npm package, treat a
push to `main` as a release action: confirm with the maintainer before pushing,
and make sure the version bump is intended.
